Pax: building a systems language from scratch

A statically typed language that keeps pointers, explicit memory management, and low-level control—while moving declaration bookkeeping, type inference, and source translation into a handwritten compiler frontend.

1. The problem Pax addresses

Systems programming requires understanding memory, representation, and execution. It does not inherently require maintaining a second copy of a function signature in a header, arranging definitions around a compiler's reading order, or repeatedly passing an array's length separately from its address. Pax begins by distinguishing low-level control from low-level ceremony.

The goal is not to conceal what the machine does. Pointers, manual allocation, structs, functions, loops, and explicit casts remain available. Instead, the language moves repetitive organisation into the frontend: resolving references to later declarations, attaching types to expressions, preserving collection metadata, and ordering generated definitions.

This makes Pax more than an alternative spelling for C. The compiler must understand the program before it can supply those conveniences. Its design combines a compact surface language with a substantial semantic implementation.

2. The language: less ceremony, explicit control

Name-first declarations and static inference

count: s64 = 42;       // Explicit type and initializer.
ratio := 3.5;          // Infer the type at compile time.
name := "Pax";
enabled := true;

The declaration shape is consistent: name, optional type, initializer. Omitting the annotation does not introduce dynamic typing. The frontend determines a concrete type and stores it in the expression's AST node. The thesis specifies s64 as the default integer-literal type, float/float32 for floating literals, string for string literals, and bool for boolean literals.

Explicit types still express constraints. A value of 100 fits into an s8 declaration; 1000 does not. Inference removes repeated information, while checking ensures that requested representations remain meaningful.

Functions, named arguments, and multiple results

divide :: (a: int, b: int) -> int, int {
    return a / b, a % b;
}

quotient, remainder := divide(20, 3);
_, remainder_only := divide(20, 3);

Functions begin with their names and use the double-colon marker. Return types follow the parameter list. Multiple results can be destructured, and the underscore discards an unwanted result. Default parameters and named arguments are resolved by the frontend and eventually become ordinary positional calls in the output.

Pointer types that read as types

pointer: ^int;
a, b, c: ^int;       // All three are pointers.
values: [4]int;      // Four integers.
pointers: [4]^int;   // Four integer pointers.

The prefix caret belongs to the type. This avoids the ambiguity of C's int* a, b, c;, where only a is a pointer. Array size and pointer composition stay next to the element type rather than being distributed around each declared name.

One member-access operator

Stats :: struct {
    score: int;
}

Player :: struct {
    stats: ^Stats;
}

// Once player.stats points to a valid Stats object:
// player.stats.score = 100;

Pax uses the dot operator for both struct values and pointers. To resolve a nested access, the analyser determines each intermediate type, follows pointer layers when required, and locates the next field. The converter later emits explicit dereferencing. The notation is simpler, but pointer validity remains the programmer's responsibility.

3. Strings, arrays, and cleanup

A string carries its byte count

string :: struct {
    count: s64;
    data: ^u8;
}

The representation keeps a byte count beside the data pointer. Code does not need to scan for a terminator merely to discover the stored length. String literals produce descriptors referring to read-only/static data; a local descriptor does not imply that the literal's bytes live on the stack.

The String.pax module implements allocation, concatenation, slicing, comparison, cloning, and destruction in Pax. New_String creates an owned copy; concat and slice produce fresh buffers rather than borrowing a subsection of another allocation. The caller releases owned results with destroy_str. The get helper performs a bounds check and returns zero for an out-of-range index.

A length-aware descriptor is not an ownership type system. The distinction between a descriptor, its referenced allocation, and that allocation's lifetime remains important. The thesis does not establish automatic prevention of all aliasing or lifetime mistakes.

Arrays preserve metadata

Pax arrays expose data and count fields and do not implicitly decay into bare pointers. A pointer to the array representation retains access to its length. This lets an array-oriented interface receive the collection without a second, independently maintained size parameter.

values: [4]int;
values[0] = 834;
array_pointer: ^[]int = &values;

for value: values {
    // Work with each element.
}

for i: 0..4 {
    // Inclusive endpoints: 0, 1, 2, 3, 4.
}

Preserving a count makes validation and traversal easier; it is not by itself proof that every indexing operation or raw pointer use is safe. Pax retains explicit low-level operations.

Defer keeps cleanup near acquisition

pointer := malloc(sizeof(int) * 10);
defer {
    free(pointer);
}

// Work with the allocation.

A deferred statement or block is scheduled for scope exit. Multiple deferred actions run in last-in, first-out order. The intended semantics cover ordinary early exits such as returns, so the generator must preserve cleanup along the relevant control-flow paths—not merely append text to the end of a block. This is explicit scope-based cleanup, not garbage collection or a guarantee of recovery after every runtime crash.

4. The frontend pipeline

.pax sources and imported modules
                ↓
        Lexer and parser
                ↓
      Abstract syntax tree
                ↓
       Symbol resolution
                ↓
  Type inference and checking
                ↓
      Resolved, typed AST
                ↓
         C converter
                ↓
  One generated translation unit
                ↓
        Backend compiler

The implementation is written in a restrained subset of C++, using templates, constructors, member functions, and shallow inheritance while remaining close to a C-style model. Lexing, parsing, analysis, and generation are handwritten without a parser generator or compiler framework. This gives the project direct control over language rules, internal representations, and diagnostics.

Lexing with source identity

Tokens carry kinds, row and column positions, and payloads such as integers, floating-point values, names, or counted strings. A union avoids reserving separate simultaneous payload storage for every literal category. Source positions are recorded immediately because every later stage may need them.

Even simple syntax introduces implementation details. The lexer must distinguish a decimal point from the range operator: 1..4 must remain an integer, a two-dot token, and another integer—not a malformed float.

Recursive descent plus Pratt expressions

Statements and declarations use recursive descent. Expression parsing originally used separate functions for precedence levels, then moved to a Pratt/top-down operator-precedence approach. The current design centralises precedence in a table while keeping a compact recursive expression routine.

// Simplified left-associative expression algorithm.
parseExpression(min_precedence):
    left = parsePrimaryOrUnary()
    while precedence(current) >= min_precedence:
        op = consume()
        right = parseExpression(precedence(op) + 1)
        left = Binary(left, op, right)
    return left

The threshold determines how tightly the right-hand expression can bind. Member access and indexing bind more tightly than arithmetic; multiplication binds more tightly than addition. Irregular statement forms remain dedicated recursive-descent routines rather than being forced into an expression-oriented technique.

One AST, progressively enriched

The AST is the frontend's shared program representation. A common node base holds a kind and source filename, line, and column. Expression nodes also carry an inferred-type field. Blocks contain statements and parent-scope links. Declarations represent variables, parameters, fields, and functions; other nodes describe calls, operators, types, structs, imports, loops, and deferred code.

Parsing creates structure. Resolution connects uses to declarations. Type analysis annotates expressions and validates operations. Generation consumes the resulting checked tree. Instead of rebuilding a different representation after every phase, Pax progressively adds meaning to a persistent, mutable AST.

5. Making declaration order irrelevant

main :: () {
    result := double(21);
}

double :: (value: int) -> int {
    return value * 2;
}

The function can appear after its use. When the first resolution traversal cannot find a declaration, it records the unresolved node and continues. Later work retries references after more declarations are known. Only after resolution fails should a genuinely missing definition become an error.

Why the saved scope matters

An unresolved name cannot be retried from an arbitrary active scope. Pax records its original lexical context. The traversal's scope stack is temporary, but AST blocks and parent links remain alive in the pool until compilation ends. Deferred lookup can therefore search as though it were still at the original reference.

This connects a visible language feature to several implementation choices: persistent blocks, scope chains, unresolved-reference queues, and shared compilation lifetime. Order independence is a semantic architecture decision, not a printing trick.

Member lookup sometimes needs inference early

For config := make_config(); followed by config.database.host, the resolver needs the return type of make_config before locating database. The thesis describes limited inference during member resolution for this purpose, followed by the broader type-analysis pass. Practical stages have explicit dependencies rather than perfectly sealed boundaries.

Structs become a dependency graph

A struct containing another struct by value requires that contained type's layout to be available. Pointer relationships are different: a linked node can point to another node without embedding it. Pax sorts definitions into dependency order for output and rejects impossible by-value cycles. The programmer can reorder valid definitions freely; the compiler cannot make an infinitely recursive embedded layout valid.

6. Turning checked programs into executable code

The project targets C so an existing compiler can handle optimisation and machine-specific generation. Pax keeps responsibility for the source language: invalid names, types, arguments, or members should be diagnosed before output. Backend rejection of supposedly valid emitted code is an implementation bug, not the intended user interface.

The converter emits boilerplate and primitive aliases, optional debug helpers, declarations, dependency-ordered structs, globals, initialisation helpers, function bodies, and startup work. Imported Pax modules are processed into the whole-program representation, so ordinary source-level header management is unnecessary.

For multiple results, the backend can return a generated struct with one field per value. A call stores that result and extracts the requested fields. For arrays, the output creates backing storage and initialises data/count metadata; global arrays require startup helpers.

The exact target dialect matters

The thesis calls the target C, but some listed output uses C++-style aggregate expressions such as string{...}, as well as nullptr. Reproducing the toolchain therefore requires the actual compiler language mode and standard, not just the label “C”. This qualification does not change the architecture: a fully analysed source program is lowered into a backend compilation language.

Single-unit output simplifies project organisation and avoids duplicating generated definitions across translation units. It should not be advertised as universally faster without clean-build and incremental-build measurements on representative projects. Foreign libraries and the backend compiler still have their own linking and platform requirements.

7. Memory allocation and profiling

Compiler objects have a useful common lifetime: most AST nodes, type information, and deferred references survive until compilation finishes, then become unnecessary together. Pax exploits this with a custom pool allocator rather than individually allocating and freeing every small object.

Bump allocation in 128 KiB blocks

The active block tracks the next address and remaining capacity. A request is rounded to eight-byte alignment, served from the current position, and advances the cursor. When space runs out, a new block is acquired. All backing blocks are remembered and freed together at the end. The default block size is 128 KiB.

The custom Array<T> uses the same pool. When it grows, it obtains a larger contiguous buffer and copies the existing elements. Superseded buffers remain allocated until bulk release. This trades temporary retained storage for simple lifetime management. Dense blocks can improve locality, although tree traversal does not guarantee adjacent access just because nodes were allocated close together.

The thesis reports approximately 4.6× faster allocation, 15.5× faster release, and 6.3× faster overall for this workload. These are allocator microbenchmark results, not an equivalent whole-compiler speedup or a universal comparison across machines.

Inspecting allocations with Perfetto

The -profile mode records allocation sequence, block, offset, size, padding, type, compiler phase, pointer, and source context. A Python conversion script turns the pipe-separated trace into Perfetto-compatible JSON. The timeline connects individual allocation patterns to expressions, node types, and phases, making block usage and alignment overhead observable.

8. Diagnostics and debugging

Source locations are preserved from tokens through AST nodes. Lexing errors cover malformed tokens; parsing errors cover grammar; resolution errors cover unknown or duplicate names and invalid member access; type errors cover incompatible expressions, arguments, assignments, and returns.

The parser attempts synchronisation after a syntax error rather than blindly interpreting every subsequent token in a damaged context. Parser, resolver, and type-checker diagnostics are buffered. The default display reports the first error in source order, while -verbose prints the collected diagnostics sorted by location for that phase.

With -debug, generated #line directives associate output statements with Pax source locations. Backend debug information can then refer to the original files rather than only to generated output. A Windows-specific crash handler walks the stack for ordinary crashes; stack overflow receives a limited dedicated message because elaborate reporting itself needs stack space.

The crash example in the thesis deliberately dereferences null. That is useful evidence of debug mapping, and also an explicit reminder that static typing and automatic dereferencing do not make Pax a fully memory-safe language.

9. Programs written in Pax

The thesis validates integration through approximately fifty positive and negative test programs, spanning more than 2,500 lines of Pax source. The abstract and later chapters vary slightly in their test-count wording; these figures describe the reported scale rather than an independently audited exact count.

Animated ASCII ray marcher

An 80×40 terminal renderer animates a lit sphere at a stated target of 20 frames per second. It combines floating-point maths, foreign functions, structs, casts, arrays, globals, pointers, and nested control flow. Frames are assembled in a buffer and printed as complete terminal output. Timing uses __rdtsc and a configured cycle budget: a demonstration of low-level access, not a portable timing library or comparative runtime benchmark.

Pluggable terminal effects

Plasma and animated-ring effects share a rendering structure while replacing the mathematical function that produces brightness. The example demonstrates reusable ordinary functions and data, not a special shader subsystem built into the compiler.

An arena allocator implemented in Pax

A separate allocator written in Pax uses linked backing blocks, aligned requests, and new blocks when capacity is exhausted. It handles oversized requests by obtaining sufficient backing storage. This is distinct from the transpiler's internal pool: one implements compiler storage, while the other is a compiled user program exercising pointers, allocation, casts, and cleanup.

Conway's Game of Life

A 50×25 world runs for 300 generations using two grids, pointer swapping, edge wrapping, and glider/blinker patterns. Unlike a stateless visual effect, it carries state forward, exercising persistent updates, indexing, and separation of current and next-generation buffers.

Library modules and rejection tests

General.pax supplies shared foreign declarations. String.pax builds string operations on the descriptor model. Sort.pax implements integer quicksort and mergesort; specialisation reflects the absence of polymorphism in the documented implementation. Negative tests deliberately contain errors that must be rejected by Pax before generation, checking the diagnostic contract as well as successful execution.

10. Results, limitations, and next steps

The project's concrete achievement is a working language frontend that combines design and implementation: syntax, semantic analysis, typed program representation, generation, diagnostics, allocator design, and integration tests. The examples show that the features cooperate in meaningful programs rather than only working in isolation.

The documented implementation is not a formally verified compiler. A test suite does not establish correctness for all possible inputs. The crash handler is Windows-specific. Memory management remains explicit. Backend code and external interfaces impose constraints. Claims of universal runtime parity, complete memory safety, or faster builds at every scale would go beyond the evidence in the thesis.

Future directions identified in the thesis include an intermediate representation and native LLVM IR or x64 backend, further use of type information for struct layout and packing, a Pax-native printing facility with automatic format selection, and a larger library implemented in Pax.

The central engineering idea

Pax does not remove the underlying work. It relocates work that can be performed consistently: infer types once instead of repeating them, sort dependencies instead of manually arranging definitions, carry lengths instead of keeping them in parallel arguments, and generate cleanup and debugging information from structured source.

The language keeps the machine visible while making the programmer manage fewer conventions that a compiler can already understand.
